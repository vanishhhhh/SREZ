# Доменные сущности

Пакет не зависит от Gin, storage и usecase. Существующие HTTP DTO и маршруты
не изменены. Поля сущностей закрыты; чтение доступно через методы и `State()`.
Снимки состояния, срезы и указатели на даты возвращаются как независимые копии.
`BrandContacts` и `BrandAppearance` — копируемые значения, валидируемые при
создании и присваивании бренду. Пустые контакты, цвета оформления, аватар и
баннер допустимы; заданные внешние URL обязаны использовать HTTPS.

## Создание, восстановление, время

`NewUser`, `NewBrand`, `NewProduct`, `NewProductColor`, `NewProductVariant`
создают объекты с ID 0. Ссылки на уже существующие сущности должны быть
положительными. Membership идентифицируется парой UserID + BrandID.

`State()` возвращает данные для будущего persistence-адаптера. Storage
назначает ID при вставке и возвращает объект через соответствующий `Restore…`.
Восстановление принимает только положительный ID и проверяет локальные поля,
статус и даты. `Restore…` предназначен для доверенных данных хранилища;
его нельзя использовать для применения входящего HTTP-запроса.

Время передаётся явно: создание требует ненулевой даты, изменение не может
предшествовать UpdatedAt. При успехе CreatedAt сохраняется, UpdatedAt обновляется;
при ошибке состояние полностью сохраняется. Цвета и варианты дат не имеют.

## Нормализация текста

Конструкторы, методы изменения и восстановление из storage обрезают краевые
Unicode-пробелы у DisplayName, имён бренда и товара, описаний, названия цвета,
Size и каждой записи Materials. Длина и обязательность проверяются после
обрезки; внутренние пробелы и регистр отображаемого текста сохраняются.
Нормализация материалов копирует входной срез и не изменяет данные вызывающего кода.

Ключи уникальности цветов и размеров — `strings.ToLower(strings.TrimSpace(value))`.
Поэтому `Красный` и ` КРАСНЫЙ ` — один цвет, `M` и ` m ` — один размер внутри
цвета. Регистр сохраняется в значении Size; свободные обозначения `One Size`,
`44 EU` и нестандартные названия поддерживаются с прежним пределом 20 символов.
Для материалов сохраняется проверка дубликатов после обрезки, с учётом регистра.

Идентификаторы Username, Slug, Category, адреса email, URL, SKU и PasswordHash
автоматически не преобразуются. Для них действуют собственные проверки формата;
хеш пароля сохраняется в точности в переданном виде.

Пароль здесь не хешируется. `PasswordHash()` и снимок предназначены для будущих
адаптеров хранения и проверки учётных данных. У поля снимка стоит `json:"-"`;
у самой сущности нет экспортируемых полей. Публичные ответы должны формироваться
отдельными DTO и не включать хеш.

## Переходы

* Brand: draft → active через `Publish`, active → draft через `Unpublish`.
  Публикация требует Name, Slug, Description и LogoURL. Изменения активного бренда
  сохраняют эти требования. Suspended восстанавливается из storage, но публичных
  методов перехода в него или из него нет.
* Editor membership: invited → active (`Accept`), invited → declined (`Decline`),
  invited/active → revoked (`Revoke`), revoked/declined → invited (`Reinvite`).
  Повторное приглашение обновляет пригласившего и дату, очищает JoinedAt и
  требует нового принятия. Owner создаётся активным; эти методы к нему неприменимы.
* Product: draft/hidden → published (`Publish`), published → hidden (`Hide`),
  published/hidden → draft (`Unpublish`). В draft и hidden допустимы нулевая цена,
  пустые Description, Category и Materials. Неизвестная непустая категория
  запрещена при любом статусе. Published требует положительной цены, непустого
  Description, допустимой непустой Category и хотя бы одного материала.

Изменение, нарушающее требования опубликованной сущности, отклоняется с ошибкой.
Поля, UpdatedAt и статус сохраняются. Автоматического скрытия или снятия с
публикации нет; `Hide` и `Unpublish` — самостоятельные явные операции.

## Membership и будущее изменение владельца

InvitedByUserID и InvitedAt — необязательная история приглашения, а не признак роли.
Они либо оба отсутствуют, либо оба заданы и согласованы по времени с JoinedAt.
Для invited/declined история обязательна, JoinedAt отсутствует; для active
обязателен JoinedAt. Revoked сохраняет реальную историю: приглашение либо
JoinedAt ранее вступившего участника.

Минимальное изменение модели не добавляет полей: бывший owner представим как
active editor с прежним JoinedAt и пустыми InvitedByUserID/InvitedAt. Его можно
отозвать, а затем пригласить заново обычным `Reinvite`. Новый owner может
сохранить реальную историю приглашения, если раньше он был editor.

Такие состояния поддерживаются `RestoreBrandMembership`; это проверка
представимости данных, а не реализация TransferOwnership. Setter роли отсутствует.
Происхождение смены роли и ровно одного активного owner нельзя подтвердить по
одной записи. Будущий usecase должен проверить право передачи, сохранить обе
membership в одной транзакции и обеспечить инвариант владельца вместе со storage.

## Контракт публикации товара

`Publish(ProductPublication, now)` принимает реальные коллекции цветов и вариантов,
а не флаг готовности. Проверяются собственные поля товара, положительная цена,
непустые описание, категория и материалы,
сохранённые ID, принадлежность цветов товару и вариантов цветам, хотя бы один цвет,
фото и вариант у каждого цвета, отсутствие повторных ID и названий цветов,
отсутствие повторных размеров внутри цвета. Названия цветов и размеры сравниваются
по нормализованным ключам. Разные цвета могут иметь одинаковый размер.
Нулевой остаток допустим.

`ValidateProductVariants` проверяет коллекцию вариантов отдельно, включая новые
варианты с ID 0. Одиночный конструктор уникальность размера не проверяет.

Usecase обязан передать **полные актуальные коллекции**, проверить активность
бренда и права, а затем сохранить результат атомарно. Проверить полноту выборки
по одному переданному срезу невозможно. `RestoreProduct` восстанавливает только
собственные поля товара и не заменяет проверку готовности к публикации.

## Граница ответственности usecase и storage

Без хранилища пакет не обеспечивает:

* существование связанных User, Brand, Product и ProductColor;
* уникальность email, username, slug и пары UserID + BrandID;
* ровно одного активного владельца бренда, создание бренда вместе с владельцем
  и атомарную передачу владения;
* авторизацию, проверку активности бренда и административную блокировку;
* полноту загруженных коллекций и защиту от конкурентных изменений.

Изменения связанных данных опубликованного товара (например, удаление последнего
фото или варианта) должны проходить через usecase: он повторно проверяет
`ValidatePublication` для полного будущего состояния и отклоняет нарушающую
требования операцию с ошибкой, сохраняя исходное состояние.
После отдельного явного снятия товара с публикации действуют правила draft/hidden;
автоматически скрывать товар запрещено. ProductColor и ProductVariant не знают
статус родительского товара. Уникальность нормализованных названий цветов и
размеров также требует ограничений storage для защиты от конкурентных записей.
