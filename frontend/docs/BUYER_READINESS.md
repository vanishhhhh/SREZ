## Что требуется для продолжения

Нужен путь к актуальной локальной копии с `docs/buyer-shopping.md` и исходной реализацией buyer API либо эти актуальные файлы в текущей копии. Одного перечисления URL недостаточно: нужны форматы ответов, точные тела mutation-запросов, ошибки и серверная семантика резервирования/отмены. Git pull, переключение веток, копирование другой версии поверх текущих изменений и создание нового backend в этой проверке не выполнялись.

После получения файлов проверяются:

1. DTO избранного и способ чтения полного набора product IDs для синхронизации кнопок и счётчика.
2. Точные cart item payloads, серверные суммы/цены, признаки недоступности, допустимое количество, поведение при изменении цены/остатка.
3. DTO заказа: статусы, позиции, суммы, время резерва, `cancel_before`, правила отмены и обновления по истечении срока.
4. Идемпотентность создания заказа и отмены, ответы при конкурентных запросах, ошибки ownership и конфликтов. После неизвестного результата POST нельзя вслепую создавать ещё один заказ.
5. Миграции и механизм освобождения резерва, безопасное изолированное окружение для проверки последней единицы товара и истечения срока.

## Согласованная цель frontend

- Избранное: общее состояние карточек/товара/страницы, активные кнопки, счётчик, удаление, приглашение гостя войти с возвратом.
- Корзина: только реальный `product_variant_id`, количество, серверные цены и итог, фото/цвет/размер, ошибки stock/price, повторное чтение после изменения.
- Заказ: `POST /orders` с JSON `{}`. Это неоплаченный резерв на 15 минут, а не платёж. Никакой формы банковских данных или придуманного списания денег.
- История/detail/отмена: сроки из ответа сервера, использование `cancel_before`, подтверждение отмены, обновление заказа и остатка после ответа backend. Таймер инициирует повторное чтение; frontend не назначает статус и не освобождает stock самостоятельно.
- Приватные запросы используют существующую auth-сессию. При logout/смене пользователя buyer-состояние и незавершённые чтения очищаются, поздние ответы другой личности не отображаются.

## План проверки после подключения backend

Изолированные Go/PostgreSQL с отдельным volume; записи создаются через API, рабочая БД и пользовательские заказы не используются. Не удалять volumes или данные.

Основной сценарий: login → товар → цвет/размер → favorite → cart variant → quantity → remove/re-add → `POST /orders {}` → подтверждённый неоплаченный резерв → история/detail → cancel → повторный GET заказа и товара с подтверждением возврата остатка.

Отрицательные сценарии: guest/expired session, другой пользователь, stock=0, stale quantity/price, двойное нажатие, гонка за последнюю единицу, неизвестный результат сети, повторная отмена, истёкший `cancel_before`, истечение резерва, loading/error/empty, desktop/mobile. Точные ожидания утверждаются по реальному контракту.
