# Переменные production на «Вольте»

Используйте отдельный серверный файл с правами `0600` вне checkout. Указывайте его явно через `docker compose --env-file /путь/к/файлу -f compose.prod.yaml`. Копия `.env.example` предназначена для локальной разработки. Переменные процесса имеют приоритет над файлом, поэтому окружение таймера должно содержать только согласованные параметры.

| Параметр | Формат и обязательность | Как получить и сохранить | Применение изменений |
| --- | --- | --- | --- |
| `POSTGRES_PASSWORD` | Обязателен, пароль действующей роли `srez` | На существующей БД используйте текущий пароль. Для чистой БД генерируйте через `openssl rand -hex 32` | Смена переменной не меняет пароль существующей роли. Согласуйте ротацию в БД и пересоздание API |
| `SREZ_JWT_KEY`, `SREZ_CSRF_KEY` | Два разных Base64 ключа, каждый декодируется минимум в 32 байта | Для нового окружения два отдельных вызова `openssl rand -base64 32`. Текущие ключи сохраняйте | Пересоздание API. Ротация влияет на JWT/CSRF |
| `SREZ_WISHLIST_KEY` | Независимый Base64 ключ ровно на 32 байта | `openssl rand -base64 32` только при первичном запуске. Хранить вместе с резервной копией конфигурации | Пересоздание API. Потеря ключа мешает восстановлению существующих ссылок |
| `SREZ_JWT_ISSUER`, `SREZ_JWT_AUDIENCE` | По умолчанию `srez`, непустые строки | Сохраните действующие значения | Пересоздание API. Изменение влияет на существующие JWT |
| `SREZ_PUBLIC_ORIGIN`, `SREZ_FRONTEND_BASE_URL` | Оба зафиксированы в Compose как `https://srez.remz.biz` без завершающего слеша | Сверьте с публичным прокси. Не дублируйте в env-файле кандидата | Согласованное изменение прокси и пересоздание API |
| `SREZ_AUTH_LOCAL_HTTP` | Зафиксирован как `false` | Production cookie имеет `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/` и префикс `__Host-`. Не задавайте `SREZ_AUTH_LOCAL_COOKIE_SCOPE` | Пересоздание API |
| `SREZ_S3_ACCESS_KEY`, `SREZ_S3_SECRET_KEY` | Обязательны. Символы `[a-zA-Z0-9/+=_.-]` | Сохраните пару действующего хранилища. Для нового окружения независимо генерируйте `openssl rand -hex 20` и `openssl rand -hex 32` | Согласованное пересоздание SeaweedFS и API |
| `SREZ_S3_ENDPOINT`, `SREZ_S3_PUBLIC_ENDPOINT` | Оба `http://seaweedfs:8333` в сети Compose | Браузер получает и отправляет файлы через публичный маршрут `/media` | Пересоздание API, если меняется внутренний адрес |
| `SREZ_S3_BUCKET`, `SREZ_S3_REGION` | По умолчанию `srez-media` и `us-east-1` | Сверить с существующим bucket и медиа в БД. Не менять bucket простым редактированием env | Пересоздание API и SeaweedFS после согласованного переноса |
| `ELASTIC_PASSWORD` | Обязателен, пароль пользователя `elastic` для bootstrap и healthcheck | Для существующего узла используйте текущий пароль. На чистом узле сгенерируйте через `openssl rand -hex 32` | Ротация пароля на узле и обновление окружения сервиса |
| `SREZ_ELASTICSEARCH_URL`, `SREZ_ELASTICSEARCH_USERNAME`, `SREZ_ELASTICSEARCH_PASSWORD` | URL зафиксирован как `http://elasticsearch:9200`. Имя и пароль обязательны | Для работы API используйте отдельную роль с `manage`, `read`, `write` для индексов и алиасов `srez-catalog-*`. На чистом узле администратор может сначала поднять `elasticsearch` и создать роль с пользователем до запуска API | Пересоздание API |
| `SREZ_SMTP_HOST`, `SREZ_SMTP_PORT`, `SREZ_SMTP_TLS` | Обязательны. DNS-имя из сертификата провайдера, порт 1–65535, `starttls` либо `tls` | Провайдер обычно выдаёт 587 для STARTTLS или 465 для TLS. Уточните реальные значения и сетевой доступ | Пересоздание API |
| `SREZ_SMTP_USERNAME`, `SREZ_SMTP_PASSWORD` | Оба заданы либо оба пустые, если провайдер явно разрешает relay без SMTP AUTH. Без CR/LF | Выделенная учётная запись у провайдера. Хранить в серверном файле | Пересоздание API |
| `SREZ_MAIL_FROM` | Обязателен, адрес отправителя или `SREZ <address>` | Подтвердите адрес/домен у SMTP-провайдера. Проверьте SPF, DKIM и DMARC у владельца домена | Пересоздание API |
| `SREZ_POSTGRES_DATA_DIR`, `SREZ_SEAWEEDFS_DATA_DIR`, `SREZ_ELASTICSEARCH_DATA_DIR` | Обязательные существующие абсолютные пути под `/data/srez` на «Вольте» | Сверить с реальными mounts и правами записи. Compose запрещает создание отсутствующих каталогов | Изменение путей требует отдельного переноса данных |
| `SREZ_FRONTEND_PORT`, `SREZ_EDGE_SUBNET`, `SREZ_FRONTEND_PROXY_IP` | Loopback-порт по умолчанию `5174`. Обязательные свободный приватный CIDR и фиксированный IP Nginx в нём | Сверить порт с внешним прокси, а CIDR с действующими сетями. Go доверяет только адресу этого Nginx | Согласованное обновление прокси, сети и контейнеров |
| `SREZ_{FRONTEND,APP,POSTGRES,SEAWEEDFS,ES}_{CPUS,MEMORY}` | Обязательные лимиты каждого сервиса. CPU в ядрах, RAM в формате Compose (`512m`, `1g`) | Владелец задаёт значения с учётом нагрузки и соседних приложений. Локальный опыт для Elastic — 1 ГиБ RAM, 2 CPU и 384 МиБ heap для небольшого каталога. Это отправная точка для измерения, а не серверный минимум | Пересоздание соответствующих контейнеров |
| `SREZ_ES_HEAP` | По умолчанию `384m`, одинаковые Xms/Xmx | Оставьте память для JVM вне heap и кэша ОС. Проверяйте с фактическим лимитом и каталогом | Пересоздание Elasticsearch |

Храните значения, содержащие специальные символы, в одинарных кавычках по синтаксису Docker Compose env-файла. Не печатайте полный результат `docker compose config`: он содержит раскрытые значения. Для проверки используйте `config --quiet`.

API проверяет цепочку сертификатов SMTP и имя сервера и использует TLS 1.2 или выше. После подключения провайдера проверьте письма подтверждения и сброса на выделенном ящике. Ссылки должны вести на `https://srez.remz.biz`. Сохраните только статус доставки и код ошибки, без письма, адреса пользователя или одноразовой ссылки. При сбое SMTP регистрация сохраняет учётную запись и показывает возможность запросить письмо повторно.
