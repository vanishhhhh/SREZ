# Архитектура и хранение данных

SREZ использует Go, Gin, PostgreSQL и sqlx. Входные HTTP-данные и JSON-ответы представлены DTO, а не сериализованными доменными сущностями.

## Слои

| Путь                           | Ответственность                                                      |
| ------------------------------ | -------------------------------------------------------------------- |
| `cmd/app/main.go`              | конфигурация, соединение, миграции, сборка зависимостей, HTTP        |
| `internal/config`              | HTTP_ADDR, DATABASE_URL; auth keys, origin, cookie mode и лимиты     |
| `internal/handler`             | маршруты, разбор запроса, DTO, HTTP-статусы                          |
| `internal/usecase`             | сценарии, интерфейсы репозиториев, межсущностные проверки            |
| `internal/entities`            | инварианты, нормализация, создание/восстановление, переходы статусов |
| `internal/storage`             | параметризованный SQL, преобразование строк БД, транзакции           |
| `migrations`                   | встроенные версионируемые SQL и runner                               |
| `cmd/seed`, `internal/devseed` | отдельная явная загрузка демонстрационных данных                     |

Пользователи хранятся через Users usecase/repository. Каталог использует BrandRepository и ProductRepository, объявленные на уровне usecase. Пакеты `project.go` и GET /projects сохранены как часть предыдущего учебного задания.

## Чтение каталога и создание draft

Публичные запросы брендов фильтруют status=active. Запросы товаров выбирают только published у active-брендов. Подробная карточка загружается четырьмя запросами в read-only REPEATABLE READ: товар с брендом, цвета, изображения, варианты. Снимок согласован; изображения отсортированы по position, варианты связаны с цветом через ID. После восстановления проверяется полный ProductPublication.

Для GET /products используется отдельная модель чтения ProductCard и метод BrowsePublic. ProductQuery валидируется в usecase; handler разбирает query-параметры и возвращает DTO. Существующие ListPublic и Products.List сохранены для прежних внутренних вызовов.

Страница каталога загружается максимум тремя SQL-запросами в одной read-only REPEATABLE READ-транзакции: количество подходящих товаров, страница товаров вместе с именами/slug брендов, затем цвета и варианты всей страницы с первыми изображениями. Для пустой страницы третий запрос не выполняется. Число запросов не зависит от количества карточек; галереи полностью не загружаются. Изображение цвета выбирается по position, обложка товара — первое существующее изображение в порядке ID цвета.

Фильтры category, brand_id и границы цены применяются до LIMIT/OFFSET. Size и color используют EXISTS, поэтому совпадения вариантов не дублируют товары и не искажают общее количество. Если заданы оба фильтра, размер должен быть в наличии именно у выбранного цвета. Значения передаются параметрами SQL; ORDER BY выбирается из закрытого списка. Каждая сортировка содержит ID как однозначный дополнительный ключ.

Создание draft через HTTP использует Management usecase: валидный Product из NewProduct сохраняется только после проверки актуального активного membership под блокировкой бренда. Draft разрешён для draft/active брендов, suspended запрещён. Старый dev-флаг удалён. Подробности — в разделе BrandMembership & RBAC Architecture.

## DTO каталога

Базовый DTO товара содержит id, brand_id, name, description, price_kopecks, category, materials, status, created_at и updated_at. Materials всегда возвращается массивом, включая пустой. Подробная карточка добавляет colors: у цвета есть id, color, images (массив HTTPS URL) и variants. У варианта — id, size, stock и sku; вариант вложен только в свой цвет. Нулевой stock сохраняется в JSON.

Карточка списка расширяет базовый DTO полями preview_image_url, brand_name, brand_slug, is_available, available_colors, available_sizes и colors. Последнее поле содержит компактные элементы: id, color, preview_image_url, is_available, available_sizes. Доступными считаются варианты со stock > 0. Общий список размеров — объединение доступных размеров, а размеры внутри цвета сохраняют их связь с цветом. Опубликованные товары с нулевыми остатками остаются в каталоге с is_available=false. Пустые массивы сериализуются как [], отсутствующая обложка — как пустая строка. JSON-состав базового DTO и GET /products/:id сохранён; POST /products сохраняет поля JSON, но требует Bearer JWT и актуальные RBAC-права.

GET /products по-прежнему возвращает JSON-массив. По умолчанию page=1, limit=20, sort=id_asc; limit ограничен 100. Метаданные находятся в заголовках X-Total-Count, X-Page, X-Limit и X-Total-Pages. Это не вводит объект-обёртку вместо существующего массива. Правила фильтрации и примеры — в [контракте каталога](catalog-api.md).

DTO бренда содержит id, name, slug, description, logo_url, banner_url, contacts (email, telegram_url, website_url), appearance (accent_color, background_color, text_color), status, created_at и updated_at. Даты передаются в RFC 3339. Данные учётных записей и membership напрямую не сериализуются.

## Схема

Все идентификаторы — BIGINT identity; цена хранится целым BIGINT в копейках, даты — TIMESTAMPTZ.

| Таблица                | Данные и ограничения                                                                                                           |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `users`                | профиль, Argon2id для регистрации, legacy-хеш ! сохранён; уникальные email/username                                            |
| `brands`               | данные бренда; contacts/appearance разложены на текстовые колонки; статусы draft/active/suspended; уникальный непустой slug    |
| `products`             | FK brand_id, цена >=0, materials TEXT[], категории и статусы draft/published/hidden                                            |
| `product_colors`       | FK product_id, color, уникальный `(product_id, color_key)`                                                                     |
| `product_color_images` | стабильный уникальный BIGINT identity id (005), FK цвета, URL, позиция 0–9; уникальные URL и DEFERRABLE PK(color_id, position) |
| `product_variants`     | FK цвета, size, stock BIGINT >=0, sku; уникальный `(product_color_id, size_key)`                                               |

CHECK также защищают порядок updated_at/created_at. Индексы покрывают FK и публичные выборки. Каскадного удаления нет. У нескольких draft-брендов может отсутствовать slug, как разрешает домен. Уникальность SKU не введена: такого доменного инварианта нет.

color_key и size_key вычисляются писателем как `strings.ToLower(strings.TrimSpace(value))`, точно как ключи уникальности в entities. Они отделены от отображаемого значения, не входят в DTO и избегают расхождений с локалью PostgreSQL. Seed и PVM storage используют одинаковое правило. При прямой записи SQL оператор отвечает за корректные ключи; такую запись следует ограничивать правами БД.

В SQL не дублируются все проверки Unicode-длины, URL, материалов и публикации: их выполняют entities. Materials сравниваются после trim с учётом регистра. Правила публикации и межсущностные гарантии описаны в [документации домена](../internal/entities/README.md).

## Миграции

Файлы `NNN_name.sql` встроены через go:embed и применяются перед открытием HTTP-порта. Номера должны иметь фиксированную ширину: порядок лексикографический.

Runner использует существующий sqlx и стандартную библиотеку. Транзакционная advisory lock сериализует старты; schema_migrations хранит имя файла, SHA-256 и время применения. Все недостающие SQL и записи журнала фиксируются одной транзакцией; ошибка откатывает новый набор. Повторный старт пропускает применённые версии. Изменённый/удалённый применённый файл и версия, добавленная задним числом, блокируют запуск. Добавляйте новую миграцию, не редактируйте применённые.

001_users.sql использует CREATE TABLE IF NOT EXISTS и поддерживает users-таблицу, созданную старым Docker initdb без журнала. Нынешний Compose не использует initdb-монтирование: миграции запускаются приложением и для существующих volumes. Не удаляйте данные ради обновления схемы.

Runner рассчитан на транзакционный DDL; CREATE INDEX CONCURRENTLY внутри него не поддерживается. Автоматического downgrade нет. Startup timeout миграций — 30 секунд. Production потребует отделить DDL-роль от runtime-роли приложения.

## Dev seed

Команда seed требует SREZ_DEV_SEED=true, применяет миграции и под отдельной advisory lock вставляет демонстрационные бренды вместе с полным каталогом в одной транзакции. Сущности восстанавливаются/проверяются через домен; публикация проверяется Product.Publish.

Существующий slug пропускается полностью. Это делает повторный seed безопасным для чужих записей, но команда не восстанавливает вручную изменённые примеры. HTTP-каталог не зависит от наличия seed-кода или моков.

Команды запуска, HTTP API, тесты и ограничения безопасности — в [README](../README.md).

### Пароли, аккаунты и адаптеры

Argon2id использует память и замедляет подбор украденных хешей. Формат PHC хранит алгоритм, версию, параметры, соль и результат. Проверка сравнивает результат constant-time. Пароль: минимум 12 Unicode-символов, максимум 1024 байта; без trim/нормализации. Проверка хеша ограничивает входные параметры (память до 64 MiB, проходы до 4, потоки до 4). При успешном входе параметры ниже baseline обновляются через compare-and-update: новый m=max(старый m,19456), t=max(старый t,2), p=max(старый p,1). Поддерживаемые компоненты не уменьшаются, верхние границы m<=65536, t<=4, p<=4 сохраняются. Mixed hash 65536/1/1 обновляется до 65536/2/1; новая соль уникальна. Повторная проверка при upgrade и вычисления ограничены тем же семафором. Для отсутствующего пользователя/нерабочего хеша выполняется dummy Argon2id. Это уменьшает, но не устраняет различия во времени запросов к БД.

Новые email: ASCII, <=254 байт, lower(trim); username: lower(trim) и прежний доменный ASCII-формат. PostgreSQL обеспечивает уникальность lower(btrim(email)) и lower(username). Миграция 003 не изменяет старые записи; конфликт блокирует весь новый набор миграций. Оператор должен проверить конфликтующие группы отдельно и подтвердить владение перед любыми исправлениями. Автоматического merge/переименования нет. Записи с `!` не могут войти; регистрация не обновляет существующую запись, а отвечает конфликтом. Восстановление доступа не реализовано.

Security adapters находятся в internal/security; JWT использует golang-jwt/jwt/v5, Argon2id — уже используемый x/crypto. Usecase.Auth координирует проверку пароля, регистрацию, login, CSRF, refresh и logout. Storage.Auth реализует параметризованные запросы и транзакции. Entities.AuthSession задаёт допустимый абсолютный срок/активность. HTTP занимается DTO, cookie, Origin и проверкой Bearer.

Argon2id ограничен семафором (по умолчанию 2 вычисления); лишние запросы получают 503 без неограниченной очереди. Login/register имеют общий локальный лимит 10 попыток/IP/минуту, ограниченный словарь 10000 IP, очистку истёкших записей. Это не распределённая защита: несколько API-инстансов увеличивают общий бюджет, перезапуск сбрасывает счётчики, ботнет обходит лимит по одному IP. Для публичного production нужен общий limiter/ограничение на proxy. Trusted proxies по умолчанию отсутствуют; произвольный X-Forwarded-For не меняет ClientIP.

### Жизненный цикл

1. Register принимает строгий JSON, валидирует Origin и поля, сохраняет новый пользовательский Argon2id-хеш, требование подтверждения и hash одноразового email-токена в одной транзакции. После commit отправляет письмо. Сессия автоматически не выдаётся; отказ SMTP сохраняет аккаунт.
2. Login проверяет пароль и допуск аккаунта по email, затем создаёт независимую серверную сессию, случайный refresh и JWT, возвращает access_token/csrf_token в JSON и ставит HttpOnly refresh-cookie. Старые required=false аккаунты сохраняют вход, новые required=true должны подтвердить почту.
3. Middleware принимает только Bearer JWT, HS256, правильные issuer/audience и обязательные корректные claims. Время жизни не более 15 минут; sub — канонический положительный int64; jti/sid — случайные 256-битные идентификаторы. JWT не содержит email, паролей, refresh или прав на бренд.
4. GET /profile читает только sub проверенного JWT и возвращает реальный статус email; PATCH /profile обновляет только display_name этого пользователя через существующий Users usecase. Аватар изменяется через Media API; avatar_url/user_id/email_verified/другие поля запрещены. Все /users HTTP-маршруты отключены, включая чтение списка. Старые методы сохранены для внутренней совместимости/тестов, но не зарегистрированы в рабочем роутере. Моковый профиль существует только в тестах.
5. После перезагрузки страницы access JWT утрачен. Frontend запрашивает GET /auth/csrf с cookie, получает HMAC(ID сессии) и вызывает POST /auth/refresh с X-CSRF-Token. GET не требует access JWT, не меняет БД и выдаёт токен только для текущего действующего refresh. Все auth/profile ответы имеют Cache-Control: no-store.
6. Refresh сначала проверяет Origin и CSRF, затем под FOR UPDATE проверяет сессию и историю хеша, помечает прежний хеш использованным и вставляет новый. В транзакции существует только один текущий хеш; новый access выдаётся после commit. Абсолютный expires_at не меняется. При утрате ответа после commit клиент может потерять сессию и должен войти повторно: сервер не хранит исходный refresh для восстановления ответа.
7. Второй запрос со старым refresh в течение 5 секунд получает 409 без cookie/нового JWT и без отзыва. Поздний replay отзывает сессию, включая текущий refresh. Сервер не может надёжно отличить украденный токен от запоздавшего легитимного запроса. Grace-окно также не гарантирует обнаружения атаки внутри этих 5 секунд. Frontend должен координировать refresh между вкладками и не повторять старую cookie бесконечно.
8. Logout проверяет ту же CSRF-привязку и отзывает только эту сессию. Повтор с той же cookie/CSRF даёт 204; после удаления cookie новый logout даёт 401. Отозванный refresh не работает. **Уже выданный access JWT отклоняется после отзыва сессии при следующей проверке middleware**. Срок JWT до15 минут остаётся дополнительной границей; уже начатый запрос не отменяется задним числом.
9. Истёкшие сессии не ротируются; login создаёт новую сессию. Автоматической очистки истории пока нет. Для production потребуется retention job и лимит числа сессий пользователя.

```mermaid
sequenceDiagram
    participant C as Browser
    participant A as Go API
    participant D as PostgreSQL
    C->>A: POST login (JSON, Origin)
    A->>D: create session + refresh hash
    A-->>C: access JWT + CSRF; HttpOnly cookie
    C->>A: POST refresh (cookie, Origin, CSRF)
    A->>D: lock session; mark old; insert new hash; commit
    A-->>C: new JWT and rotated cookie
    C->>A: POST logout (cookie, Origin, CSRF)
    A->>D: revoke session
    A-->>C: 204 + clear cookie
```

### Origin, cookie, CORS

Для POST auth endpoints Origin обязателен и должен точно совпадать с SREZ_PUBLIC_ORIGIN, в том числе для CLI. Для read-only GET /auth/csrf отсутствие Origin разрешено: браузеры могут не отправлять его в обычном same-origin fetch. Явно указанный Origin (включая null) обязан точно совпадать с конфигурацией. Исключение зарегистрировано только на этом GET-маршруте и не ослабляет POST. При наличии Sec-Fetch-Site разрешён только same-origin; cross-site, same-site, none и неизвестные значения отклоняются, независимо от Origin. Отсутствующий Fetch Metadata допустим: при отсутствии обоих заголовков GET использует действующую refresh-cookie, а доступ стороннего браузерного JS к ответу ограничен Same-Origin Policy без CORS. Это совместимость со старыми/небраузерными клиентами, а не доказательство происхождения. GET не изменяет состояние сессии, не обновляет cookie и сохраняет Cache-Control: no-store. Bearer GET/PATCH /profile не требует Origin и не использует refresh-cookie. Для POST auth требуется application/json. Refresh/logout дополнительно требуют refresh-cookie и сессионный X-CSRF-Token. Origin не является доказательством личности для небраузерного клиента; доказательства — секретные токены.

Локальный HTTP разрешается только точным SREZ_AUTH_LOCAL_HTTP=true и origin на localhost/loopback; имя cookie тогда srez_refresh_local, Secure=false. Иначе допустим только HTTPS, cookie использует __Host- и Secure. Очистка повторяет имя/Path/Domain/Secure/SameSite. Срок cookie — оставшийся абсолютный срок сессии. Продакшен-значений ключей/fallback в исходниках нет, отсутствующие/некорректные ключи блокируют запуск приложения.

Same-Origin Policy ограничивает чтение ресурсов браузерным JS; CORS регулирует исключения для такого чтения. SameSite ограничивает отправку cookie между сайтами, но сайт не равен origin. CSRF-защита проверяет конкретный запрос на сервере; JWT аутентифицирует Bearer. CORS/SameSite не заменяют CSRF или авторизацию. План: https://srez.ru/ — React, /api/* — Go за reverse proxy; браузер видит один origin, CORS не требуется. В локальной интеграционной копии React использует Vite proxy: localhost:5174, /api с rewrite на Go8081 и /media без rewrite. changeOrigin:false сохраняет Origin; проверки CSRF/JWT не отключены.

### Threat Model

### Компромиссы и границы

JWT подтверждает подписанную личность, а middleware дополнительно проверяет активную серверную сессию. Logout, reset и обнаруженный refresh replay отзывают access при следующем запросе; права на бренд всё равно берутся из PostgreSQL. Серверные сессии без JWT остаются допустимой более простой альтернативой. Refresh непрозрачный, потому что все нужные состояние/отзыв уже в БД; SHA-256 подходит только для случайных высокоэнтропийных токенов, не для паролей. HttpOnly не мешает JS отправлять запросы. LocalStorage/sessionStorage сохраняют украденный JS-токен дольше и не используются; память также не устраняет XSS.

Implemented означает покрытие существующими автоматическими проверками, но не независимую сертификацию безопасности. Локальные nginx/CSP, email verification и password recovery реализованы; production инфраструктура, распределённый общий auth limiter, cleanup/retention и управление сессиями остаются отдельными задачами. Email quota уже сохраняется в PostgreSQL. PVM реализован в существующей RBAC-границе, подробности ниже. Старый required=false аккаунт не доказывает владение email; для восстановления доступа требуется отдельный безопасный процесс. Публичный запуск до отдельного AppSec-ревью не рекомендуется.

Источники решений: [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [JWT library API](https://pkg.go.dev/github.com/golang-jwt/jwt/v5).

## BrandMembership & RBAC Architecture

### Роли и статус реализации

**Implemented:** PostgreSQL memberships, private endpoints, приглашения, отзыв, транзакционная object-level authorization. JWT подтверждает личность, а не текущие полномочия бренда. В JWT роли брендов не добавлены. Все private endpoints используют Bearer middleware; usecase повторно проверяет роль/статус в БД внутри транзакции.

| Операция                                      | Guest | User без membership     | Active editor | Active owner |
| --------------------------------------------- | ----- | ----------------------- | ------------- | ------------ |
| Публичный каталог                             | да    | да                      | да            | да           |
| Создать новый бренд                           | нет   | да                      | да            | да           |
| Свои бренды / manage                          | нет   | только свои memberships | свой бренд    | свой бренд   |
| Настройки/publish/unpublish бренда            | нет   | нет                     | нет           | да           |
| Пригласить/отозвать editor, список участников | нет   | нет                     | нет           | да           |
| Draft/редактирование/публикация товаров       | нет   | нет                     | свой бренд    | свой бренд   |

Invited/declined/revoked не дают editor-прав. Для suspended бренда операции управления товарами запрещены. Manage бренда позволяет участнику увидеть состояние блокировки; изменение настроек/publish/unpublish suspended запрещено. Публикация товара требует active бренда, draft можно готовить в draft/active бренде.

### Схема и жизненный цикл

004_brand_memberships.sql добавляет PK(user_id,brand_id), FK пользователей/бренда/пригласившего, CHECK role/status/временных полей. PK покрывает поиск по user_id, отдельный индекс — brand_id/user_id. Частичный UNIQUE(brand_id) для active owner запрещает двух владельцев. CHECK не позволяет owner стать revoked/declined. Модель допускает исторические приглашения/бывшего owner-editor как существующий домен, но API смены ролей нет.

POST /brands создаёт Brand.NewBrand со статусом draft и NewOwnerMembership в одной транзакции. При ошибке membership вся вставка откатывается. Owner нельзя назначить клиентским JSON. API не создаёт orphan-бренды; SQL unique обеспечивает максимум одного owner, а exactly-one при создании обеспечивает транзакционный сценарий. Удаления/отзыва owner и ownership transfer нет: они требуют отдельного многострочного сценария и ревью.

Owner приглашает зарегистрированный username: NewEditorInvitation → invited. Только адресат выполняет Accept → active или Decline → declined. Owner делает Revoke для invited/active editor → revoked. Повторное приглашение revoked/declined вызывает Reinvite и требует нового Accept. Повтор active/invited даёт 409; PK предотвращает дубли. Приглашение самого себя/владельца запрещено. Все переходы используют существующие методы домена.

GET /me/brands возвращает active memberships; GET /me/brand-invitations — invited. DTO включает бренд/роль. GET members owner-only отдаёт user_id, brand_id, роль, статус и даты/метаданные приглашения без данных учётной записи. Объекты entities напрямую не сериализуются.

### Транзакции, блокировки и TOCTOU

ManagementRepository.WithinBrand — небольшая транзакционная граница для usecase callback, без универсального permission engine. Единый порядок:

1. Строка бренда FOR UPDATE.
2. Membership текущего пользователя, затем целевого участника, если нужен переход.
3. Товар FOR UPDATE с проверкой его фактического brand_id.
4. Для публикации: цвета по ID FOR UPDATE, изображения по color_id/position FOR UPDATE, варианты по ID FOR UPDATE.
5. Доменные методы, SQL-запись и commit; при любой ошибке rollback.

Все операции одного бренда, включая принятие/отзыв приглашения, сериализуются строкой бренда. Поэтому разные порядки доступа к двум memberships не образуют цикл: в один момент только одна такая транзакция владеет брендом. Между брендами операции не берут вторую блокировку бренда. Частные чтения также используют эту границу для простоты согласованной политики.

При revoke vs update возможны два корректных порядка: операция editor фиксируется до revoke либо после revoke получает 404. После завершившегося revoke старый JWT не предоставляет права. Проверка отдельно от commit не используется. Защита проверена интеграционно, включая детерминированный ожидающий update за блокировкой с последующим revoke.

Для PATCH/publish/hide/unpublish бренд сначала определяется по существующему product_id, затем блокируется, товар перечитывается с условием brand_id и блокируется. Предварительное чтение brand_id не является проверкой прав: всё решение принимается под блокировками. PATCH не принимает brand_id. При публикации загружается полный реальный агрегат и вызывается Product.Publish; client is_ready/коллекции не принимаются. Блокировки родителей также блокируют конкурентные вставки через FK, блокировки дочерних строк — их изменения до commit. Public GET использует тот же загрузчик коллекций без write-lock в своём read-only snapshot.

**Limitations:** операции одного бренда сериализуются, это уменьшает пропускную способность, но упрощает доказательство актуальности прав. Транзакции READ COMMITTED. Управляющие запросы должны быть короткими; нагрузочное тестирование и production HTTP/DB timeouts — отдельная инфраструктурная работа. Прямые административные SQL-записи не являются безопасным API: будущие редакторы вариантов обязаны соблюдать тот же порядок и заново валидировать полный агрегат. Нельзя считать приложение защищённым от оператора с произвольными правами SQL.

### Ошибки и защита объектов

401 — нет JWT. Для отсутствующего membership или invited/declined/revoked private ресурс скрывается как 404, равно как отсутствующий объект. Editor, уже имеющий доступ к бренду, при owner-only действии получает 403. Suspended продуктовые операции — 403. Некорректные поля/ID — 400, состояние/slug/повторный переход/неполная публикация — 409. DTO не раскрывают SQL, пароль или токены.

Strict JSON и лимит 64 КиБ сохраняются. POST создания бренда принимает только name/slug; PATCH бренда только предусмотренные поля. Contacts/appearance заменяются целиком при передаче объекта. PATCH товара принимает только name/description/price_kopecks/category/materials. POST-переходы принимают `{}`; изменения не выполняются через GET. Все эти операции аутентифицированы Bearer, cookie не является источником полномочий, поэтому CSRF-контракт auth-cookie операций не изменён.

### Legacy brands и доверенный backfill

Миграция не назначает владельцев старым/seed-брендам. Публичные чтения сохраняются, но пользователь не может присвоить такой бренд. Отдельного backfill HTTP endpoint нет.

Операторский процесс (не автоматическая миграция): получить подтверждение владения вне приложения, проверить конкретные user_id/brand_id и согласование команды, сделать резервную копию, открыть транзакцию, заблокировать конкретный бренд FOR UPDATE, убедиться в отсутствии owner, вставить валидный active owner с joined_at/created_at/updated_at и зафиксировать проверяемый аудит назначения. При конфликте rollback; никогда не использовать массовый backfill на «первого пользователя». Прямая запись допускается только доверенному оператору и не является частью пользовательского API. Интеграционные тесты назначают owner seed-бренду исключительно внутри своей изолированной схемы для проверки полного агрегата.

### Следующий этап

**Implemented:** полный CRUD цветов, изображений и вариантов с теми же locks/проверкой ProductPublication; новый draft можно полностью подготовить через HTTP. **Implemented locally:** frontend с координацией токенов, приглашениями и PVM. **Planned:** отдельный аудит Auth+RBAC+PVM. Нет ownership transfer, email-рассылки или глобального admin. Существующие ограничения JWT/logout, refresh grace и локального auth limiter остаются в разделе Authentication.

## Product Variant Management

PVM расширяет существующий Management usecase, ManagementTx и PostgreSQL managementTx. Отдельного permission engine или параллельного storage-слоя нет. Handler регистрирует 13 маршрутов через существующую цепочку Bearer → managementReady и использует отдельные DTO. ProductVariantTx объединяет интерфейсы дочернего CRUD; его реализует та же транзакция WithinBrand.

Management.withProduct находит фактический бренд, под его блокировкой повторно проверяет membership, блокирует товар и загружает полный ProductPublication прежним загрузчиком. Он проверяет принадлежность цвета товару и варианта/изображения цвету. После записи у published-товара заново читает агрегат и вызывает ValidatePublication, затем Touch/SaveProduct. При нарушении инвариантов весь SQL откатывается. Порядок блокировок и семантика 401/403/404/409 сохранены. Нулевой stock допустим. Добавление пустого цвета к published требует предварительного явного hide/unpublish.

005_product_image_ids.sql добавляет фотографиям постоянный ID, сохраняя URL, позиции и связи. Старый составной PK сохраняется по составу, но становится DEFERRABLE INITIALLY IMMEDIATE. Storage временно откладывает проверку позиций при добавлении/перемещении, сохраняет полный порядок через unnest WITH ORDINALITY и возвращает IMMEDIATE. Изображения не пересоздаются, ID не меняются. URL-unique, FK и диапазон 0–9 остаются. Удаление цвета явно удаляет его детей в той же транзакции, без каскадной миграции. Миграции 001–004 не изменены.

Публичные DTO сохраняют URL-массивы, а management-DTO изображений содержат id/product_color_id/url/position. Публичная загрузка каталога по-прежнему ограничена тремя SQL-запросами, детальная карточка использует прежний snapshot. CRUD обновляет updated_at родительского товара только после успешной проверки.

Контракты, схема взаимодействия, ошибки, тесты и Windows PowerShell: [product-variant-management.md](product-variant-management.md).

### Финальные меры аудита и отложенный deployment hardening

Recovery и access logging не печатают сырые URL/query, заголовки, cookies, тела или значения panic. Recovery пишет только фиксированный тип события и stack frames без аргументов/исходных строк; клиент получает обобщённую ошибку, broken connection не вызывает повторной записи ответа. Это проверяется синтетическими секретами в debug/release, включая EPIPE/ECONNRESET.

R2 остаётся deployment risk, не production-ready: необходимо настроить HTTP ReadHeader/Read/Idle deadlines, DB pool budget, context/lock/statement timeouts, proxy connection/body limits и распределённый limiter. Locking protocol RBAC сохранён. Возможный deny-only precheck membership до ожидания lock не должен заменять авторитетную проверку внутри транзакции. Нагрузочное тестирование и production proxy/TLS вне текущего этапа.

## Избранное и авторизованная корзина покупателя

Сценарий `Shopping` определяет правила покупателя и интерфейсы
`ShoppingRepository` и `CartTx`. Пакет `entities` проверяет количество (1–100)
и выполняет целочисленные денежные расчёты с защитой от переполнения.
`handler` отвечает за DTO, строгий разбор ввода, ID покупателя из Bearer JWT
и HTTP-ошибки; `storage` — за SQL, преобразование строк и транзакции.
При запуске `Shopping` подключается до регистрации маршрутов в `EnableAuth`.
Существующие DTO и права каталога, авторизации и RBAC сохранены.

Миграция 006 добавляет `favorites` с составным первичным ключом
`(user_id, product_id)` и внешними ключами, а также `cart_items` с внешним ключом
пользователя, допускающей NULL ссылкой на вариант, CHECK количества
и `UNIQUE(user_id, product_variant_id)`. Избранное загружает сохранённые ID
и публичные карточки `ProductCard` в одном снимке REPEATABLE READ с общей пакетной
загрузкой дочерних данных — не более трёх запросов. Для приватных товаров
карточка равна null. Корзина читается в снимке одного SQL-запроса; непубличные
поля скрываются на уровне SQL, а `usecase` рассчитывает доступность и суммы.
В итог входят только публичные позиции с достаточным остатком.
Корзина никогда не резервирует остатки.

Изменения корзины получают транзакционную advisory-блокировку по отрицательному
ID покупателя, затем блокировки каталога в порядке бренд → товар → дочерние
данные до изменения строк корзины. Проверки и запись выполняются в одной
транзакции, включая расчёт итоговых сумм. Конкурентные приращения сериализуются
и дополнительно защищены уникальным ключом БД. Все запросы и изменения корзины
содержат `user_id`. Добавление в избранное блокирует бренд и товар для проверки
актуального статуса публикации и использует `ON CONFLICT DO NOTHING`.

При удалении варианта или цвета PVM явно обнуляет затронутые ссылки корзины
на варианты до их удаления в существующей транзакции управления каталогом.
Недоступные строки корзины остаются удаляемыми; ошибка проверки публикации
восстанавливает ссылки. Строки корзины не блокируются раньше каталога,
поэтому порядок бренд и дочерние данные → обнуление ссылок корзины не создаёт
цикла блокировок с операциями покупателя. Ограничивающие внешние ключи
предотвращают неподдерживаемое прямое удаление. Существующие блокировки
управления каталогом сохранены. Контракты, примеры и тесты приведены
в [документации покупателя](buyer-shopping.md), включая ограничение из-за
отсутствующей командной спецификации v0.3.

## Транзакционное оформление заказа и история покупателя

Сценарий `Orders` координирует `CheckoutTx` и `OrderRepository`;
сущность `entities.Order` проверяет неизменяемые снимки позиций и итоговые суммы
с защитой от переполнения. Обработчики заказов разбирают строгое тело `{}`,
формируют DTO и ошибки, получают покупателя из существующего обработчика
Bearer JWT. Хранилище заказов переиспользует транзакцию `WithinCart`
и advisory-блокировку сценария `Shopping`.

Внутри транзакции оформление определяет нужные ресурсы, блокирует все бренды
по возрастанию ID, затем товары, цвета, изображения и варианты в существующей
иерархии до изменения строк корзины. Все поддерживаемые операции управления
каталогом сначала блокируют один бренд; оформление с товарами разных брендов
сортирует все блокировки брендов, исключая циклы. Запись корзины и оформление
используют общую advisory-блокировку пользователя, поэтому одна корзина
не может быть куплена дважды или изменена добавлением одновременно с покупкой.
Фактическая собственная корзина, статусы публикации и брендов, актуальные цены
и остатки перечитываются после получения блокировок; предварительный запрос
ресурсов и предыдущий HTTP-ответ корзины не служат источником этих данных.

`usecase` отклоняет пустую корзину, недоступные позиции или недостаточный
остаток и создаёт один неоплаченный `Order` с товарами разных брендов.
`storage` условно уменьшает доступный stock с проверкой достаточности
и собственной корзины, создаёт заказ, снимки, резервы и удаляет только оформленные
строки. Всё выполняется в одном sqlx.Tx; ошибка или отмена контекста до commit
откатывает остатки, резервы, заказ и очистку корзины. Последнюю единицу может
зарезервировать ровно один покупатель; проигравший получает 409 и сохраняет
корзину. Резерв не означает оплату. Немедленный повтор оформления получает
ошибку пустой корзины (409); ключи идемпотентности пока не поддерживаются.

Миграция 007 добавляет `orders` (внешний ключ пользователя, статус, итог и время)
и `order_items` (внешний ключ заказа, исторические ID бренда, товара и варианта,
название товара, цвет, размер, количество, цену и сумму позиции).
ID каталога намеренно не имеют внешних ключей на текущие записи: история
сохраняется после удаления, снятия с публикации и редактирования каталога.
Сущности заказа копируют состояние; снимки и итог неизменяемы, а отдельный
доменный переход разрешает самостоятельную отмену неоплаченного заказа.
История читается SQL-запросами с ограничением по покупателю: заказы и все позиции
загружаются двумя пакетными запросами в одном снимке REPEATABLE READ только
для чтения. Список отсортирован по убыванию ID и пока не имеет пагинации.
Каждый приватный маршрут возвращает `Cache-Control: no-store`.
Объединение гостевых корзин, оплата, обработка заказов брендами, частичная отмена
и доставка не реализованы; открытые вопросы и ограничения исходных материалов
зафиксированы в [buyer-shopping.md](buyer-shopping.md).

## Резервы, отмена и автоматическое истечение

Товар резервируется на 15 минут с момента создания unpaid-заказа.
`stock` — свободные единицы, исключая активные резервы. Миграция 008 добавляет
order_reservations, сроки/времена отмены и истечения и статусы cancelled/expired.
Исторические unpaid уже уменьшали stock: их позиции оформляются резервами
без повторного изменения количества. После запуска сервис освобождает
просроченные резервы. Миграции 001–007 сохранены; 008 ещё не публиковалась.
Перед обновлением остановите старые экземпляры API; смешанные версии запрещены.

POST /orders/:id/cancel использует существующий Bearer, строгий DTO `{}`
и Orders.Cancel. Доменный Order.Cancel проверяет unpaid и окно 15 минут;
Order.Expire проверяет достижение срока. Оба сохраняют снимки и сумму.
Storage WithinOrder сначала получает все блокировки брендов по ID, затем
товары, цвета, изображения, варианты и принадлежащий заказ FOR UPDATE.
Затем только активные записи order_reservations получают released_at;
их количества возвращаются в доступный stock, статус заказа сохраняется.
Любая ошибка откатывает всё. Повторы и гонка отмены с истечением не увеличивают
остатки дважды. Переполнение даёт конфликт и сохраняет резерв для разбора.
Существующий порядок блокировок управления каталогом не изменён.

FK резерва указывает на историческую пару order_id/variant_id в order_items,
а не на живой вариант. Явное удаление PVM не блокируется неожиданным FK;
отменённый/истёкший заказ не воссоздаёт удалённые варианты. Сохранившиеся
варианты получают резерв обратно, а снимки заказа остаются читаемыми.

cmd/app запускает Orders.RunReservationExpiry сразу после сборки зависимостей.
Проходы выполняются немедленно и каждые 5 секунд; до 100 заказов в пакете,
10 секунд на проход. Usecase выбирает просроченные ссылки через DueOrders
и для каждой использует WithinOrder и доменный Expire в отдельной транзакции.
Все изменения включают владельца в SQL. Глобальная выборка DueOrders доступна
только внутреннему сервису, HTTP-маршрута для неё нет. Несколько экземпляров
координируются теми же блокировками. Ошибки журналируются фиксированным событием
без SQL и данных покупателя; неудачные операции повторяются следующим проходом.

Маршруты изменения избранного и удаления позиции корзины без тела отклоняют
переданные данные с 400, применяя общий лимит 64 КиБ. Авторизация, refresh/logout,
публичные DTO каталога и безопасные журналы сохраняют свои контракты.

Начало обработки, реальная оплата и подтверждение продажи ещё не реализованы.
Платёжный путь должен согласоваться с блокировками заказа/резерва, не оплачивать
отменённое или истёкшее состояние и не уменьшать свободный stock второй раз.
Банковский чарджбэк нельзя запретить кодом приложения. Порядок поддержки и
несогласованные меры описаны в [chargebacks-and-support.md](chargebacks-and-support.md),
результаты аудита — в [transaction-security-audit.md](transaction-security-audit.md).

## Media Ownership / Phase 2

`Media` — отдельный usecase поверх существующего Management/RBAC и sqlx
managementTx. Прямой presigned upload API отключён. Backend принимает только
ограниченный raw File/Blob, проверяет и нормализует его до первого S3 PUT.

Миграция 010 добавляет `media_assets` (физический объект и immutable target),
`media_upload_requests` (техническое состояние загрузки) и FK-ссылки avatar/logo/
banner/product image. Deferred SQL checks требуют ready + ровно одну правильную
доменную ссылку при commit. Publication вычисляется по текущему состоянию сущности.
Detach ставит asset на удаление в той же транзакции; worker выполняет S3 DELETE
только после commit и повторной проверки отсутствия ссылок. Processing имеет TTL,
а неоднозначный commit не вызывает немедленного удаления объекта.

Write-policy остаётся прежней: avatar только actor, оформление brand — owner,
фото product/color — active owner/editor. Brand → membership → product → children
блокируются существующим withProduct; upload/request → asset добавляются после
них. Avatar использует user FOR NO KEY UPDATE. GC не держит asset-lock во время
S3 I/O и обновляет upload state после освобождения asset-lock, без инверсии порядка.

Legacy HTTPS validation не ослаблена: доменные источники разделены на URL и
managed reference. HTTP DTO сохраняют прежние поля, формируя относительный
media proxy URL для managed записей. Ни HTTP URL, ни CDN hostname не являются
постоянным идентификатором S3-объекта в БД.

Подробности: [модель, API, лимиты и recovery](media-storage.md),
[проверки](media-storage-validation.md), [security review](media-storage-security-review.md).

После независимого аудита: admission разделён на один upload и два delivery
slots; startup консервативно проверяет ACL/policy; runtime проверяет сохранённый
bucket. Миграция 011 отделяет обязательную очистку (100) от конечного resweep (10,
24 часа), с наблюдаемым backlog. [Обоснования и регрессии](media-storage-audit-fixes.md).

## Подтверждение email (17.11.2026)

В существующий Auth добавлен EmailVerification usecase с интерфейсом MailSender. Repository атомарно создаёт pending user + hash challenge и подтверждает email; SMTP запускается только после commit. MailSender реализован отдельным internal/mailer через SMTP, text/HTML, timeout5s и проверяемый TLS для внешнего провайдера. Новая014 сохраняет legacy users required=false/date=NULL, новые registration=true. Login проверяет email после пароля; CreateSession/Rotate дополнительно проверяют eligibility в PostgreSQL. Argon2id, JWT/CSRF/refresh rotation сохранены.

Resend ротирует challenge под user lock, сохраняет account/IP quotas в PostgreSQL и возвращает uniform202 без обещания доставки; отправка асинхронная in-memory, без plaintext outbox. Frontend fragment очищается до router, секрет остаётся только в памяти страницы, подтверждение только POST по кнопке. Mailpit1.34.0 закреплён digest, имеет отдельные mailbox volumes/loopback ports для working, QA и Go tests. Контракты, лимиты и Windows команды — в [email-verification.md](email-verification.md).

## Password Recovery и немедленный отзыв

Миграция015 добавляет purpose-separated password_reset_tokens и persistent IP quota. Сброс использует общий MailSender/SMTP и Argon2 semaphore; под user lock атомарно меняет hash, погашает challenge и отзывает все сессии. Login CreateSession сверяет ожидаемый password_hash, refresh соблюдает user → session lock order. Bearer проверяет session ID/user/expiry/revocation/email одним indexed SELECT, timeout2s, без stale cache. Pool ограничен20 соединениями. Новый reset не подтверждает email и не создаёт сессию.
