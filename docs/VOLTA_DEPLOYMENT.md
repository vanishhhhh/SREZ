# Production SREZ на «Вольте»

Публичный адрес — `https://srez.remz.biz`. Этот репозиторий содержит кандидат `compose.prod.yaml`. Действующие настройки «Вольты» имеют приоритет до сверки с Романом. Команда разработки работает через GitHub, доступ по SSH предусмотрен для владельца инфраструктуры.

## Маршрут запроса и данные

Серверный reverse proxy принимает HTTPS и отправляет запросы на `127.0.0.1:5174` или согласованный loopback-порт. Контейнер Nginx обслуживает React SPA, снимает префикс `/api` при передаче в Go и передаёт `/media` без изменения пути. Origin браузера сохраняется. На серверном прокси нужно заменить полученный от клиента `X-Real-IP` адресом подключения, либо адресом клиента из явно доверенного вышестоящего прокси. Сохраните публичный Host. В API доверенным отмечен ровно фиксированный адрес frontend-контейнера. HTTPS-режим cookie определяется конфигурацией и не зависит от клиентского заголовка `X-Forwarded-Proto`.

PostgreSQL 16, SeaweedFS и Elasticsearch обслуживаются на закрытой сети проекта. Приложение дополнительно подключено к frontend-сети для доступа к SMTP. Хранилища привязаны к существующим каталогам в `/data/srez`, заданным в серверном env-файле. В кандидате SMTP отправляется на реального TLS-провайдера. Mailpit используется только в изолированных тестах. Не включайте в логи внешнего прокси URL, cookies, Authorization и тела запросов SREZ. Для этой площадки прокси может отключить обычный access log либо записывать только статус, длительность и объём ответа без пути и query.

Elasticsearch выполняет фильтрацию и сортировку каталога, PostgreSQL остаётся источником данных. При первом каталожном запросе Elasticsearch строит индекс из PostgreSQL. Один только `/api/health` не заменяет проверку каталога. Если Elasticsearch настроен и недоступен, каталог возвращает 503. HTTP между Go и Elasticsearch остаётся в закрытой сети SREZ и защищён учётными данными. Сверьте поддержку Docker Compose, DNS Nginx `127.0.0.11`, свободный CIDR, лимиты и `vm.max_map_count` на узле, где запускается Elasticsearch. Для Podman локальный smoke не подтверждает совместимость.

## Что выявил аудит репозитория

`compose.yaml` задаёт локальный адрес и публикует API и PostgreSQL. `compose.integration.yaml` использует локальный HTTP, Mailpit, пробрасывает внутренние порты на loopback и отключает аутентификацию Elasticsearch. `compose.frontend.yaml` дополняет локальный setup, а `compose.qa.yaml`, `compose.tests.yaml` и `compose.media-test.yaml` обслуживают тестовые данные и порты. Для «Вольты» требуется отдельный Compose.

Go применяет миграции в транзакции и проверяет контрольные суммы уже применённых SQL. Изменений SQL в этом релизе нет. Nginx уже обслуживает повторную загрузку маршрутов SPA и сохраняет query при проксировании. Production-кандидат добавляет проверку готовности Go и проверку API через frontend. Существующий SMTP-клиент проверяет сертификаты и поддерживает TLS/STARTTLS. Конфигурация теперь требует зашифрованный SMTP и общий origin сайта и писем в HTTPS-режиме.

## Релиз и первый запуск

Фича-ветка → PR → CI → согласованный merge в `main` → серверный `deploy.sh`. Владелец сервера подтверждает состояние таймера, который по договорённости проверяет GitHub примерно каждые 10 минут. GitHub Actions собирает и тестирует приложение в изолированной среде. Перед первым запуском используйте [чек-лист владельца](VOLTA_OWNER_ACTIONS.md) и [описание переменных](volta-env-requirements.md).

Владелец подтверждает имя действующего Compose-проекта перед запуском. Пример ниже использует имя кандидата `srez-prod`; при существующей установке используйте её имя. Интегрируйте следующие команды в согласованный `deploy.sh`:

```sh
docker compose -p srez-prod --env-file "$SREZ_ENV_FILE" -f compose.prod.yaml config --quiet
docker compose -p srez-prod --env-file "$SREZ_ENV_FILE" -f compose.prod.yaml build --pull app frontend
docker compose -p srez-prod --env-file "$SREZ_ENV_FILE" -f compose.prod.yaml up -d --wait --wait-timeout 210
```

Каждый запуск `deploy.sh` сериализуется, например через `flock`. Скрипт берёт проверенный SHA из `origin/main`, собирает образы до переключения и записывает SHA успешного релиза после smoke-проверки. Если сборка или запуск завершились ошибкой, владелец проверяет статус контейнеров и журнал миграций до повторного запуска. Сохраняйте предыдущую рабочую конфигурацию и ссылки на образы. Уточните в расписании, что запуск вне окна обслуживания допустим.

Проверьте снаружи `https://srez.remz.biz/api/health` и `/api/products?limit=1`, затем главную, каталог, карточку и изображения. Тестовой учётной записью пройдите регистрацию, подтверждение email, вход, перезагрузку приватной страницы, вишлист и публичную ссылку, корзину, заказ с отменой и студию. Проверьте письмо сброса пароля. Убедитесь, что HTTP переводит на HTTPS, сертификат действителен и backend принимает только настроенный Origin. Проверка реального SMTP зависит от настроек провайдера.

## Откат, диагностика и резервные копии

Для релиза без изменения схемы откатите PR через новый PR с теми же проверками. При ошибке схемы остановите обновления таймера, проверьте `schema_migrations` и совместимость предыдущего приложения с уже изменённой схемой. Готовьте исправляющую миграцию с новым номером. Git revert не откатывает применённый SQL, а старый бинарник может отказать при незнакомой миграции. Восстановление БД выполняет владелец по отдельной согласованной процедуре с оценкой потери записей после снимка.

Логи и состояние контейнеров запрашиваются у Романа. Ночное резервное копирование PostgreSQL и медиа выполняет владелец сервера. Перед первым релизом подтверждаются последняя копия, проверка восстановления и сохранность ключей. Индекс Elasticsearch восстанавливается из PostgreSQL.

## Защита main

В GitHub `Settings → Rules → Rulesets` сначала проверьте активные правила для `main`. Создайте или дополните branch ruleset со статусом **Active** и целью `main`. Включите **Require a pull request before merging**, **Require status checks to pass before merging**, **Require branches to be up to date before merging**, **Restrict deletions** и **Block force pushes**. Bypass list оставьте пустым без согласованного исключения. Уберите автоматический merge, если он включён и команда его не согласовывала.

В workflow `SREZ checks` задачи `backend`, `frontend`, `browser` и `production-compose` запускаются на PR без фильтров по путям. Выберите GitHub Actions как источник обязательных проверок, если это доступно. Сделайте `backend` и `frontend` обязательными. Включите `browser` и новую `production-compose` после первого зелёного прогона и появления точных названий, особенно учитывая, что merge запускает публикацию. См. [GitHub rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets).
