## Potential Risks

- **R-01 · MITIGATED.** `SREZ_BRAND_PAGE_SCHEMA_MAX_WRITE` ограничивает save и publish. Вариант приложения с лимитом 2 читает сохранённые V1, V2 и V3. Если опубликованный снимок повреждён или неизвестной версии, публичное чтение отдаёт обычную витрину бренда и пишет диагностику с ID. Draft остаётся закрытым. PostgreSQL и HTTP проверяют совместимость, лимит и fallback. До production необходимо подтвердить версию rollback image в deployment и настроить мониторинг диагностики.
- **R-02 · MITIGATED.** Go по-прежнему допускает две параллельные доставки. Web Locks координируют управляемые загрузки вкладок профиля. Браузерные native-запросы и независимые контексты ограничиваются сервером. Проверены повторы 429 и отдельные клиенты. На трёх независимых контекстах фиксировались реальные 429, проверяемые изображения восстанавливались. Для production нужны метрики занятых слотов, 429, исчерпанных повторов, CPU и RSS при конкурентном трафике.
- **R-03 · DEFERRED.** Чтение редактора по-прежнему использует транзакцию управления с блокировкой строки бренда. Измерения ожидания блокировки уровня p95 отсутствуют. Более узкую read-only транзакцию стоит рассмотреть по метрикам, сохранив чтение роли и страницы из одного снимка и сериализацию записи с отзывом прав.

## Architecture

### Доставка и хранение

Go сначала выполняет обычную проверку доступа по ID asset. Для нормализованных `brand_banner` и редакционных фото выбирается один из трёх разрешённых размеров, 480, 960 и 1440 px. Увеличения исходника нет. JPEG кодируется с качеством 82, PNG сохраняет прозрачность. Размеры покрывают колонку mobile при DPR 1, типичные карточки и мобильный DPR 2, широкую desktop-обложку при DPR 1. Ширина 1440 ограничивает вес на широких экранах и при высоком DPR.

Производная существует только после востребованного GET и сохраняется в приватном SeaweedFS под детерминированным ключом. Проверка существования повторяется под блокировкой строки готового asset. Удаление использует тот же жизненный цикл и блокировку. GC удаляет исходник и до трёх производных, включая повторную обработку. Существующие assets получают варианты лениво. Перенос или обновление таблиц для производных не требуется.

Сервер проверяет доступ к каждому URL, включая открытый браузером hero. Используется обычный маршрут Media API и `Cache-Control: no-store`. Оригинал, производные и ключи объекта остаются под той же моделью доступа. Исключительно статические JS/CSS в `/assets/` сжимаются Nginx. Правила доставки Media API и приватных API по-прежнему отдельные.

### Ревизии и неопределённая запись

Загрузка регистрируется до первого сетевого запроса. Изменения полей могут продолжаться во время записи. Ответ обновляет опорную revision и применяет нормализованный draft, когда за время запроса в форме не появился новый локальный объект. Конкурентные записи по-прежнему проходят серверный compare-and-swap. Для восстановления после обрыва сравнивается конфигурация нужного снимка с отправленным состоянием с учётом нормализации. При конфликте форму можно прочитать и скопировать, а загрузка серверной версии требует подтверждения сброса локальных правок.

### Deploy и rollback

1. Выбрать и проверить rollback image с миграциями 016/017, чтением V1–V3, безопасным публичным fallback и очисткой производных в GC.
2. Сначала развернуть V3-совместимые readers с `SREZ_BRAND_PAGE_SCHEMA_MAX_WRITE=2`. Проверить чтение существующих снимков и роли. Лимит применяется к записи и публикации. Уже записанные V3 продолжают читаться.
3. После обновления всех инстансов разрешить запись с лимитом 3. При откате использовать только V3-совместимую сборку. Лимит 2 можно включить для остановки новых V3-записей. Исторические снимки и SQL-миграции сохраняются.

## UX

Studio и публичная витрина используют один renderer. На мобильном переход из настроек переносит фокус в выбранную секцию. Кнопка возврата восстанавливает фокус инициатора, а изменение порядка сохраняет привязку фокуса к тому же блоку. Заголовки и сетки построены по CSS брейкпоинтам публичной страницы.

Публикация фиксирует порядок, вид блоков, цвета и редакционные фото. Название, описание, контакты, логотип, основной баннер и публичные товары меняются после сохранения в своём разделе. Предпросмотр берёт доступные текущие данные бренда и локальную композицию.

В QA сверены раскладки четырёх опубликованных композиций и скриншоты Studio и витрины СМЕНЫ. У КОНТУРА — центрированный Story и вертикальный ритм, у ПОЛЮСА — раздельная обложка и горизонтальная галерея, у СМЕНЫ — редакционная Story и асимметричные сетки, у ОСНОВЫ — чередование полноширинного кадра и текстовых секций. Строка товаров сохраняет четыре колонки на desktop и две на mobile. Варианты фото в СМЕНЕ сохраняют различимость ткани и мелких деталей на 390 и 1440 px при DPR 1. На больших DPR и особенно при агрессивном crop чёткость ограничена доступной шириной исходника и максимальным вариантом.

[Галерея финального QA](release-evidence/brand-page-builder/README.md) включает Studio, мобильный preview и публичные композиции.

## Вердикт

1. **Гонка upload/save закрыта.** Детерминированная проверка подтвердила блокировку save/publish во время загрузки и сохранение новых правок после позднего ответа. Отмена и ошибка снимают блокировку. После смены бренда старая форма не применяется.
2. **Неопределённый результат обрабатывается.** Потеря ответа после commit save и publish восстанавливает revision. Конкурентное изменение сохраняет локальные правки в форме и требует явного разрешения конфликта.
3. **Мобильные бюджеты выполнены на QA.** LCP 2,06–2,09 с в одиночных прогонах. У тяжёлой страницы 1,91 МБ медиа mobile и 5,70 МБ desktop. Худший зафиксированный LCP для серии 15/40 с тремя независимыми контекстами — 3,404 с.
4. **Нативная публикация hero допустима.** Доступ проверяется в Go на каждом GET. Приватный предпросмотр использует авторизованную доставку. ACL, ограничения объекта и очистка проверены в интеграции.
