# SREZ · Финальный аудит Brand Page Builder

## Executive summary

База проверки — `b284645464e6e102388ac3bb6ca24d3df4c0ec4e`. В актуальном main присутствуют macOS Support (#14) и Fashion UI (#15). Аудит выполнен поверх `feat/brand-page-builder-foundation`. Основная база на 5174 использовалась только для чтения. Тестовые записи, письма и остановки сервисов выполнялись в изолированных средах QA и tests.

## Architecture review

- Studio держит локальную конфигурацию отдельно от подтверждённого серверного draft. Запись и публикация проходят через синхронные блокировки операций и серверную проверку ревизии. После неопределённого результата UI сверяет нормализованный snapshot и ревизию. Чужая ревизия с другим содержимым вызывает конфликт и сохраняет локальные поля.
- API проверяет ограничение тела, единственное значение JSON, точные имена ключей, дубликаты, вложенность и форму объектов до декодирования DTO. Go-модель независимо проверяет схемы V1–V3, типы блоков, допустимые пресеты, пропорции и пределы. Публичный маршрут выбирает опубликованный снимок и при ошибке чтения отдаёт стандартную витрину.
- Управляющая транзакция сериализуется по бренду, проверяет активное членство, считывает draft и публикует его вместе со ссылками на медиа. Снимки хранятся раздельно. Публичные товары, название, описание, баннер, логотип и контакты остаются живыми. UI Studio объясняет этот контракт.
- Preview применяет публичный renderer и CSS в sandboxed iframe 1440×900 или 390×844. Для черновых фото используется авторизованный запрос. Геометрия сверяется при фактической ширине iframe. Приватная обложка preview ограничена вариантом 960 px.
- PostgreSQL подтверждает состояние asset и наличие текущей ссылки перед доставкой. Нативный hero использует `srcset` и высокий приоритет, редакционные фото загружаются по видимости через управляемую очередь. Go ограничивает две параллельные доставки. Производные в SeaweedFS создаются лениво по трём фиксированным размерам, без произвольного пользовательского ключа. Блокировка готового asset координирует создание производной с GC.

## Deployment и данные

Миграции `016_brand_page_builder.sql` и `017_brand_editorial_media.sql` добавлены в конец. Исторические миграции сохранены. Проверены чистая БД, снимок журнала 001–015 с существующими брендами и товарами, повторное применение, параллельный запуск, транзакционный откат при ошибке и целостность журнала. PostgreSQL-тест `TestPostgresBrandPageUpgradeFromMain` проверяет точный путь 015 → 017. Legacy-бренды продолжают читаться без строки в `brand_pages`.

Образ для rollback обязан включать миграции 016/017 с теми же контрольными суммами. Старый бинарник main завершится на проверке неизвестной строки журнала, даже с лимитом записи 2 и до первой записи V3. Совместимый образ также должен читать V1–V3 и очищать media derivatives. На первом этапе установить `SREZ_BRAND_PAGE_SCHEMA_MAX_WRITE=2`, затем после проверки всех readers в целевом окружении разрешить 3. Локальная транзитная проверка write gate выполнена, целевой production rollback image отдельно проверить перед включением V3.
